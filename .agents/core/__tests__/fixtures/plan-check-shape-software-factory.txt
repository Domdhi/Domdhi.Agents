## Executive Summary

Domdhi.Agents already has a harness, a dependency graph (Story Index, waves, `/review:optimize-backlog`), an independent review cadence, a real judge (`gate.js` with receipts) and an improvement loop (`/sweep`, `/review:evolve-skills`, the differential eval). What it lacks is what turns a semi-automatic assistant into a factory: **"done" a program can check**, **walls that are structure rather than requests**, **a trigger that needs no human at the keyboard**, and **a loop that measures and improves the agents without letting them edit their own judge**.

This TODO reuses and fixes what exists. Four epics, each a stage of the research plan:

1. **SF-1 Executable done and real walls (10 stories).** Each acceptance criterion gets a `verify:` command; a recorded red run; a mechanical ship check that backs the prose `SHIP_CHECK_OK`; a failure-signature ledger with a one-shot stronger-tier retry; walls for subagent writes, `permissions.deny`, and one action-authority matrix.
2. **SF-2 The graph you already have, tightened (6 core + 1 later).** A deterministic `plan-check` helper replacing "write a short script", a `needs output of` vs `merely after` story field, derived waves, per-story checkpoints keyed by input hash, worktree per overlapping writer.
3. **SF-3 Automated starts (8 core + 1 later).** A run record and run id, row stamping and a run trace, a gate-state detector feeding `/listen`, a headless contract for `/do` and `/run-todo`, and a documented scheduled detect-only run (a systemd timer on WSL). The fix-on-a-branch trigger is a later slice.
4. **SF-4 Self-improvement (5 core + 6 later).** Core measures whether the agents are good (scoreboard, structured issue log, protected set, an accept/reject verdict, intake fixes). The later slice, behind a ship gate, lets the loop run: a persistent regression suite with a held-out split, an apply helper that restores on failure, a ledger, and a scheduled propose-only cycle.

**Wave shape: role-based within each epic, ordered by hotspot** — 20 waves; core (29 stories) is waves 1 to 15, later (8 stories) is waves 16 to 20. the owner chose to run everything in one pass (Owner Decision 1), so the ship gate after wave 15 is pre-approved. The order still holds for a reason: every later step depends on executable done and real walls, and the self-modifying part comes after the measurement it depends on.

## Seams and Main Flow

**Seams.** Each is defined once here; stories reference it by name.

* **`verify:` binding** — one command per acceptance criterion, written inline on the AC checkbox bullet as `verify: <command> => exit N` (default `=> exit 0`). Written by `/todo` and `/create-project-epics-todo` authoring (SF-1.7), parsed by `todo-completion.js` into a `verify` field on the criterion object (SF-1.1), executed by `ac-verify.js` (SF-1.1). The text must never contain a checkbox marker (`status.js:307` and `metrics.js:241` match one unanchored on every line under a story). A criterion without one is `manual` (or `[CI-pending]`) and never fails the run.
* **ac-verify record** — `docs/.output/.state/telemetry/ac-verify/{storyId}.json`: `story, acLine, command, expectedExit, exit, met, status (ran|refused|timeout|tree-changed), durationMs, outputTail (≤2 KB), codeHash, head, ranAt`; `met` is true only when `status` is `ran` and `exit` equals `expectedExit`. `codeHash` is `codeTreeHash` from `gate-receipt.js` (SF-1.1): the tree hash excluding `docs/.output/`, `docs/work/`, `docs/TODO_*.md` and explicit extra paths, i.e. everything a wave edits after its gate. Also `{storyId}.freeze.json` (check-file blobs, a hash of the `verify:` lines, and a re-baseline history). Written by `ac-verify.js` (SF-1.1, SF-1.2); read by `ship-check.js` (SF-1.3).
* **ship seal** — `docs/.output/.state/telemetry/ship-seal.json`: `head, receiptId|null, mode (receipt|summary), codeHash, recordsHash, docs, sealedAt`. `codeHash` uses the same `codeTreeHash` as the ac-verify records; `recordsHash` hashes the ac-verify records on disk at seal time. Written by `ship-check.js seal` (SF-1.3) after the last code edit, which is after the Step 7 review fixes; read by `ship-check.js verify` and `commit.js --ship-check` (SF-1.4). A project that does not use receipts gets `mode: summary` (lower assurance, documented); `shipCheck.enabled: false` in the gate config turns the check off. Wiring in the workflows is SF-1.6 and SF-1.7.
* **failure ledger** — `docs/.output/.state/telemetry/gate-failures.jsonl`, rows `{ts, head, sig, legs, passed, killed}` plus optional `cls` (`environment`) and `log` (absolute log path); `head` is a working-tree identity using the `codeTreeHash` exclusions, not the commit id; a passing run writes a `passed: true` row (it resets the streak) and a killed or timed-out run writes a neutral row with `killed` set (wave 1 review F13). Written once per failing gate run by `gate.js` through `_lib/failure-ledger.js`, and by `failure-ledger.js record --output-file` for a failing focused run (SF-1.5). Read by `damage-control.cjs` (SF-1.5), the retry dispatch's `PRIOR FAILURE` block (SF-1.6), the budget printer (SF-1.5), the run record (SF-3.1), the issue-log signature (SF-4.2) and the intake gate-failure signal (SF-4.5). Counting rule: same signature on a changed tree is a genuine repeat; same signature on the same tree is a no-op; differing outcomes on the same tree is flaky. Flaky and environment classes never count toward escalation. A pass resets the streak; KILLED and TIMED OUT are neutral.
* **plan `**Budget:**` line** — `**Budget:** attempts=3 gate-failures=6 dispatches=40 minutes=240` (comma or space separated; `attempts` = two standard attempts plus one `deep`-tier subagent attempt per story). Defined in the run-plan template (SF-1.6); parsed by `parseBudget` in `failure-ledger.js` (SF-1.5), which `run-record.js` imports (SF-3.1); exhaustion is computed by `failure-ledger.js budget` (exit 12). One budget shape and one parser.
* **plan Wave Log lines** — `- **Red:**` (SF-1.6), `- **Story checkpoints:** {ID}={hash12}@{receiptId}` (SF-2.5). The completion section gains one tracked `**Run record:** {json}` line (SF-3.1). No per-story files and no second tracker (`run-todo` workflow rule at line 850).
* **run id and session pointer** — run id seeded from the plan stamp (`_lib/run-stamp.js`); pointer `docs/.output/.state/telemetry/current-run-{session_id}.json` `{run_id, plan, wave, story, since}`. Written by `run-record.js` (SF-3.1), whose `start` is called when the plan is created so the pointer exists for the whole run (SF-3.6); read by the row writers (SF-3.2, SF-3.3). An env var cannot carry it (the Bash tool keeps no shell state).
* **run result and exit codes** — `run-record.js finish` exits 0 passed, 1 failed, 2 invalid input, 10 needs-human, 11 blocked, 12 budget-exhausted, 13 killed (distinct from `gate.js` exit 3 for a held lock). Consumed by the headless contract (SF-3.6), the scheduled recipe (SF-3.8), the scoreboard (SF-4.1) and the propose-only cycle (SF-4.11).
* **`**After:**` story field** — optional soft ordering. `**Dependencies:**` means "needs output of" (every existing TODO already treats it so). Defined in the story template (SF-2.2); read by `plan-check.js` (SF-2.1 parses, SF-2.2 documents). It never creates a `DEP_ORDER` error.
* **gate signal** — `gate-signal.js` JSON `{state: green|red|killed|stale|unknown, signature, reason, ts, failureNames[]}`; seen-state file `docs/.output/.state/telemetry/listen-gate-seen.json` holds the last recorded signature. Defined in SF-3.4; consumed by `/listen` (SF-3.5).
* **protected set** — the single list of paths no improvement run and no subagent may edit: gate, hooks, guardrail rules, settings, eval tasks, holdout, grader prompts, judge code. Enforced two ways: `subagentReadOnlyPaths` in the path hook (SF-1.8: the gate, its judges, hooks, guardrail rules and settings) and `improvement-scope.js assertDiffInScope` (SF-4.3: adds tests, judge code, eval tasks and holdout, and covers Bash writes after the fact). SF-4.3 depends on SF-1.8 so no entry is defined twice; its own `guardrail-rules.yaml` edit is Main Agent direct because SF-1.8 puts that file in the subagent tier.
* **action-authority matrix** — T0 free, T1 cheap undo, T2 outward, T3 irreversible; columns action, tier, undo cost, approver, enforcement point. Home is a new section in `.agents/startup-reference.md` (SF-1.10); the scheduled recipe (SF-3.8) and the apply helper (SF-4.9) cite it and never restate it.

**Main flow, end to end.** `/todo` writes a story with a `verify:` per AC and, where relevant, an `After:` (SF-1.7, SF-2.2) and `plan-check` validates the plan (SF-2.1). `/run-todo` derives waves (SF-2.3), starts a run record (SF-3.1, SF-3.6), writes tests, records the red run (SF-1.1, SF-1.6), dispatches in an isolated worktree when writers overlap (SF-2.6), gates, runs `ac-verify`, seals and commits through `commit.js --ship-check` (SF-1.3, SF-1.4). A failed gate feeds the ledger (SF-1.5); the second identical failure gives a `deep`-tier subagent one attempt with both prior failures; the third stops. A story skipped on resume is checked against its input hash (SF-2.4, SF-2.5). Rows carry the run id (SF-3.2, SF-3.3) and a run trace is assembled (SF-3.7). A scheduled job runs `/listen gate --only-if-red` (SF-3.4, SF-3.5, SF-3.8), writes an intake item, and a human decides. The scoreboard (SF-4.1) turns run records into "are the agents good"; the issue log (SF-4.2), intake (SF-4.5), verdict (SF-4.4) and protected set (SF-4.3) make the improvement loop trustworthy; the later slice runs it (SF-4.6 to SF-4.11). Every step has an owner; the apply and trigger stories that touch code unattended are `later`.
